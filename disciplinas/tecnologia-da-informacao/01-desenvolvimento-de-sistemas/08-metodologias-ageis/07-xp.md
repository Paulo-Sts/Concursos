# Engenharia de Software Extreme Programming

## 1. Fundamentos do Extreme Programming
- O Extreme Programming (XP) é reconhecido como o método ágil mais conhecido e utilizado na atualidade.
- A abordagem foi concebida para levar práticas de desenvolvimento iterativo a níveis considerados extremos.
- O método foca na execução de práticas que garantem a produção de um software de alta qualidade.
- Existe um limite rigoroso para a carga de trabalho, pois o excesso é visto como prejudicial à qualidade da produção intelectual.
- O XP preconiza o desenvolvimento de várias versões de um sistema, que podem ser integradas e testadas em um único dia.

## 2. Práticas e Princípios Fundamentais
- O desenvolvimento no XP é regido por um conjunto de práticas técnicas e comportamentais integradas.

| PRINCÍPIO OU PRÁTICA | DESCRIÇÃO |
|---|---|
| Planejamento incremental | Requisitos gravados em cartões de estória e divididos em tarefas técnicas |
| Pequenos releases | Entregas frequentes de conjuntos mínimos de funcionalidades que agregam valor |
| Projeto simples | Foco exclusivo nas necessidades atuais do sistema sem antecipar mudanças futuras |
| Desenvolvimento test-first | Implementação de testes automatizados antes da construção da funcionalidade |
| Refatoração | Melhoria contínua do código para simplificação e manutenção da qualidade |
| Programação em pares | Desenvolvedores trabalham em duplas verificando e apoiando o trabalho mútuo |
| Propriedade coletiva | Responsabilidade compartilhada onde qualquer desenvolvedor pode alterar o código |
| Integração contínua | Sincronização constante do trabalho ao sistema validada por testes de unidade |
| Ritmo sustentável | Rejeição de horas extras excessivas para preservar produtividade e qualidade |
| Cliente no local | Representante do usuário disponível integralmente como membro da equipe |

## 3. Dinâmica do Processo XP
- Os requisitos são expressos através de estórias do usuário, que representam cenários discutidos com o cliente.
- As estórias do usuário são registradas em cartões conhecidos como CRC.
- O ciclo de vida de um release segue um fluxo específico de atividades:
  - Seleção de estórias do usuário para o ciclo atual;
  - Divisão das estórias em tarefas menores;
  - Planejamento do release;
  - Desenvolvimento, integração e testes do software;
  - Liberação do software para o cliente;
  - Avaliação do sistema para realimentar o próximo ciclo.

### 3.1 Detalhamento das Práticas Técnicas
- TDD (Test Driven Development) ⟶ técnica de desenvolvimento onde os testes são escritos antes do código da funcionalidade.
- Refatoração ⟶ processo de lapidação do código para evitar sua degeneração com o passar do tempo e dos incrementos.
- CI/CD (Continuous Integration e Continuous Delivery) ⟶ base da automação para colocar o software em produção sem riscos de quebras.
- Padrões de codificação ⟶ prática necessária para permitir que todos os desenvolvedores realizem alterações em qualquer parte do código.

> [!TIP] DICAS: 
> - O representante do cliente no XP é o responsável por definir os testes de aceitação (ATDD) do sistema.
> - A propriedade coletiva do código exige que a equipe estabeleça padrões de codificação claros desde o início do projeto.
> - Lembre-se que o XP utiliza estórias de usuário e não listas formais de requisitos.

> [!CAUTION] OBSERVAÇÃO: 
> - A refatoração não serve para adicionar novas funcionalidades, mas sim para manter ou melhorar a qualidade interna do código existente.
> - Em concursos, é comum a afirmação correta de que o XP motiva projetos simples que não contemplam requisitos futuros inicialmente.
> - A integração contínua exige que todos os testes de unidade passem com sucesso após a incorporação de um novo código.
