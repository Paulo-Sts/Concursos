# Extreme Programming (XP): Detalhamentos Complementares

## 1. Cartões CRC e Projeto Simples
- O princípio KISS (Keep It Simple, Stupid) deve ser seguido rigorosamente para manter o projeto simples.
- Não se deve acrescentar funcionalidades extras.
- Cartões CRC significam Classe, Responsabilidade e Colaboração.
- Permitem identificar e organizar as classes para o incremento sendo desenvolvido.
- São o único artefato de projeto produzido como parte do projeto XP.
- Exemplo de cartão CRC:
  - Nome da Classe: Pedido.

| RESPONSABILIDADE | COLABORAÇÃO |
|---|---|
| Verifica se item está em estoque | LinhaDetalhe |
| Determina preço | LinhaDetalhe |
| Verifica pagamento válido | Cliente |
| Envia para endereço destino | |

> [!CAUTION] OBSERVAÇÃO:
> - O projeto XP segue rigorosamente o princípio KISS.
> - Não se deve prever funcionalidades futuras; atender apenas às necessidades atuais.

## 2. TDD e Ciclo Red-Green-Refactor
- O ciclo do TDD segue rigorosamente Red, Green, Refactor.
  - Red: escrever o teste de unidade que falha;
  - Green: escrever o código de produção mínimo para o teste passar;
  - Refactor: reestruturar o código de produção e o código de teste sem alterar seu comportamento funcional, melhorando legibilidade, reduzindo duplicação e otimizando o design interno.
- A refatoração no TDD ocorre após o código ter sido escrito e testado.
- A prática de test-first complementa o framework Scrum e pode aumentar a qualidade do incremento, sem alterar os eventos ou artefatos do Scrum.

> [!CAUTION] OBSERVAÇÃO:
> - No TDD, a refatoração não ocorre antes de qualquer código ser escrito; ela acontece após o código ser escrito e testado.
> - Test-first não é a mesma coisa que testes de aceitação.

## 3. Refatoração: Definição e Importância
- Refatoração é o processo de mudar um sistema de software de tal forma que não altere o comportamento externo do código, embora melhore a estrutura interna.
- A refatoração mantém a semântica do código; após as mudanças, o código ainda funciona da mesma forma.
- A refatoração é uma técnica disciplinada para reestruturar um corpo de código existente, alterando sua estrutura interna sem alterar seu comportamento externo.
- O desenvolvimento iterativo e incremental aumenta a importância da refatoração, pois os requisitos são priorizados e refinados ao longo de várias iterações.
- A refatoração é potencializada pela adoção contínua do TDD, visando manter a qualidade e a simplicidade da base de código ao longo das iterações.

> [!CAUTION] OBSERVAÇÃO:
> - Refatorar não é modificar o comportamento interno e externo mantendo a estrutura interna; é o oposto: altera a estrutura interna sem alterar o comportamento externo.

## 4. Programação em Pares: Papéis e Objetivos
- Os desenvolvedores trabalham em pares, um verificando o trabalho do outro e fornecendo apoio para realizar sempre um bom trabalho.
- Eles utilizam o mesmo mouse, teclado e monitor.
- O par se alterna nos papéis de condutor e navegador.
- Um dos objetivos é otimizar a qualidade do código produzido devido ao mecanismo de inspeção em tempo real.
- Programar em dupla num único computador assegura que o código seja sempre revisto por duas pessoas.
- Todo o código-fonte de produção deve ser implementado em programação em pares.

> [!TIP] DICAS:
> - Programação em pares = duas pessoas, um computador, revisão em tempo real.
> - Papéis: condutor (escreve) e navegador (revisa).

## 5. Propriedade Coletiva: Abrangência
- A equipe é coletivamente responsável pelo código do projeto, encorajando a colaboração e reduzindo a dependência em indivíduos específicos.
- Os pares de desenvolvedores trabalham em todas as áreas do sistema, de tal maneira que não se formem ilhas de conhecimento, com todos os desenvolvedores de posse de todo o código.
- Qualquer um pode mudar qualquer coisa.
- No XP, todos os desenvolvedores da equipe devem possuir autorização para modificar, consertar ou refatorar partes do sistema.

## 6. Integração Contínua: Detalhes Operacionais
- A equipe integra o código frequentemente para garantir que o software esteja sempre em um estado utilizado.
- Tão logo o trabalho em uma tarefa seja concluído, este é integrado ao sistema como um todo.
- Depois de qualquer integração, todos os testes unitários do sistema devem ser realizados.
- A prática na qual os desenvolvedores mesclam suas alterações de código-fonte em um repositório central, disparando testes automatizados a cada modificação para detectar erros o mais rápido possível, denomina-se integração contínua.
- Todo o código desenvolvido pelo time é incorporado em um repositório comum várias vezes ao dia, garantindo que problemas de integração sejam notados e corrigidos rapidamente.

> [!CAUTION] OBSERVAÇÃO:
> - Integração contínua não é implantação contínua nem publicação contínua.
> - A integração de código não deve ser feita apenas nos computadores dos desenvolvedores; é no repositório central.

## 7. Testes de Aceitação
- São ligados às user stories.
- Buscam testar o sistema do ponto de vista do usuário.
- Objetivam validar com o cliente o que foi definido nos requisitos do software, verificando se o produto desenvolvido está de acordo com o que foi estabelecido.
- As funcionalidades do sistema são validadas, as entradas podem ser simuladas e o comportamento de saída pode ser observado.
- O sistema é testado com todos os componentes interligados e configurados, inclusive bancos de dados e gerenciadores de filas, garantindo que cada serviço oferecido está funcionando.

## 8. Outras Observações
- O XP busca atender às necessidades atuais, e nada mais.
- O XP requer a disponibilidade de um representante do cliente a todo o tempo (on-site customer).
- O XP não realiza testes de integração apenas ao final de todo o desenvolvimento.
- O XP valoriza o trabalho em equipe, não o trabalho individualizado.
- A filosofia da modelagem ágil admite decisões que levem um projeto à rejeição e à refatoração.
