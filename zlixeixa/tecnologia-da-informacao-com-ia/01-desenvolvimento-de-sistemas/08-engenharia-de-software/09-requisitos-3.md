# Engenharia de Software - Requisitos 3

## 1. Visão Geral do Processo
- A engenharia de requisitos pode incluir quatro atividades de alto nível.
- O processo é iterativo, não linear, com atividades intercaladas.
- Cada atividade produz um entregável (artefato).

## 2. Atividades de Alto Nível do Processo
- Estudo de viabilidade: avalia se o sistema é útil para a empresa.
- Elicitação e análise de requisitos: descoberta e compreensão dos requisitos.
- Especificação de requisitos: documentação dos requisitos.
- Validação de requisitos: verificação se os requisitos estão corretos.

## 3. Visão em Espiral
- O processo é iterativo, com idas e voltas entre as atividades.
- A quantidade de tempo e esforço dedicado a cada atividade varia conforme o estágio do processo.
- No início: maior esforço em requisitos de negócio e não funcionais em alto nível.
- Mais tarde: maior esforço em requisitos de sistema detalhados.
- É possível, por exemplo, estar no estudo de viabilidade e voltar para entender melhor a especificação de requisito de negócio.

> [!TIP] DICAS:
> - A visão em espiral reflete a natureza não linear e iterativa da engenharia de requisitos.
> - O processo de engenharia de requisitos é complexo e envolve negociação constante com os stakeholders.

## 4. Atividades do Processo de Elicitação e Análise de Requisitos
- Esta atividade é dividida em quatro etapas que ocorrem de forma iterativa.

### 4.1 Descoberta de Requisitos
- Interação com os stakeholders para descobrir seus requisitos.
- Requisitos de domínio também são descobertos durante esta atividade.
- Existem várias técnicas complementares que podem ser usadas.

> [!CAUTION] OBSERVAÇÃO:
> - Elicitar é sinônimo de exprimir, fazer aparecer. Não confundir com o processo de compra chamado de "licitação".

### 4.2 Classificação e Organização de Requisitos
- Agrupa requisitos não estruturados em grupos coerentes.
- A forma mais comum é usar um modelo de arquitetura do sistema para identificar subsistemas.
- Na prática, a engenharia de requisitos e o projeto da arquitetura devem andar juntos.

### 4.3 Priorização e Negociação de Requisitos
- Requisitos de diferentes stakeholders podem entrar em conflito.
- Envolve priorização de requisitos e resolução de conflitos por meio de negociação.
- Os stakeholders precisam se encontrar para resolver diferenças e chegar a um acordo.
- Às vezes, é necessário escolher um gestor do sistema para priorizar demandas.

> [!TIP] DICAS:
> - A negociação de requisitos pode levar à eliminação, combinação ou modificação de requisitos até que se atinja um grau de satisfação.
> - Requisitos conflitantes devem ser discutidos em termos de prioridade, avaliando custos, riscos e conflitos internos.

### 4.4 Especificação de Requisitos
- Os requisitos são documentados e inseridos no próximo ciclo da espiral.
- Podem ser produzidos documentos formais ou informais de requisitos.

## 5. Abordagens de Análise
- Análise Estruturada versus Análise Orientada a Objetos.
- A questão não é qual é a melhor, mas sim que combinação de representações dará o melhor modelo.
- Equipes de TI geralmente optam por uma abordagem e excluem as representações da outra.

## 6. Panorama da Engenharia de Requisitos

### 6.1 O que é?
- Conjunto de tarefas que levam ao entendimento do impacto do software sobre o negócio.
- Busca compreender o que o cliente quer e como os usuários finais interagirão com o software.

### 6.2 Quem realiza?
- Engenheiros de software (também chamados de engenheiros de sistemas ou analistas).
- Outros interessados no projeto: gerentes, clientes, usuários finais.

### 6.3 Por que é importante?
- Projetar um programa que resolva o problema errado não atende às necessidades de ninguém.
- É fundamental entender o que o cliente quer antes de projetar e construir o sistema.

### 6.4 Etapas envolvidas
- Concepção: define o escopo e a natureza do problema.
- Levantamento: ajuda os interessados a definir o que é necessário.
- Elaboração: refina e modifica os requisitos básicos.
- Negociação: define prioridades, o que é essencial e quando é necessário.
- Especificação: o problema é especificado de algum modo.
- Validação: revisão para garantir que o entendimento do problema coincida entre as partes.

### 6.5 Artefato
- Objetivo: fornecer um entendimento escrito do problema para todas as partes.
- Pode ser alcançado por meio de: cenários de uso, listas de funções e características, modelos de análise ou uma especificação.

### 6.6 Como garantir que o trabalho foi realizado corretamente?
- Os artefatos são revisados com os interessados.
- Após o acordo, as coisas continuarão mudando ao longo de todo o projeto.

> [!TIP] DICAS:
> - Validação de requisitos envolve verificar se os artefatos estão de acordo com o padrão esperado e identificar inconsistências.
> - Revisão técnica é um procedimento utilizado para validar os requisitos de um projeto.
> - Verificação e validação são atividades distintas no V & V.
